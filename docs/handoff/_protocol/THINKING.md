# 思想 · 为什么是这套流程

> 这份文档记录推导过程与取舍，而不是操作步骤。步骤见 `QUICKSTART.md`，规则见 `PROTOCOL.md`。
> 目的：当你在真实仓库里遇到协议没覆盖的情况时，知道**该往哪个方向改**，而不是机械照抄。

## 0. 问题与原始假设

- 目标：让 DeepSeek 干活，拿到 Opus 80~90% 的 UI / 动效效果。
- 约束：Opus 的 token 太贵，不能让它写完整实现。
- 原始假设：**Opus 先写到"能跑通的 70%"，再交给 DeepSeek 收尾。**

我们保留了这个直觉（先贵后便宜），但把"70%"从**代码量**换成了**判断边界**。原因是下面第 1 节。

## 1. 成本模型：贵的模型该买什么

一个 UI 任务里的工作可以拆成三类：

| 类型 | 例子 | 谁做更划算 | 为什么 |
|---|---|---|---|
| **判断** | 配色定调、动效曲线选型、布局取舍、"够不够高级" | **Opus** | 判断错了，后面所有代码全错；返工成本乘以重复次数 |
| **复制** | 第 2~20 个同构组件、断点收敛、补 hover 态 | **DeepSeek** | 确定性工作，照抄即可；Opus 做它没有额外收益 |
| **试探** | 试某种效果能不能实现 | 便宜模型先试 | 试探是消耗性的，花在贵模型上是纯损耗 |

**结论 1：Opus 的边际价值在两端最密**——开头（定调）和结尾（终审），中间是凹的。

**结论 2：一刀切 70% 的结构性缺陷**——它把"最后 30% 是否忠于原意图"这个**纯判断问题**交给了最便宜的模型。这正是 DeepSeek 最容易跑偏的地方，也是返工最贵的地方。

**结论 3：所以形状不是三段线性，而是"判断 → 复制 → 判断"**，复制段可以很长（50~65% 工作量），判断段很短但必须在两端。

> 你的 70% 可以原样保留成 P1 的加强版（规范 + 3 个参照实现 + 全屏带真实交互），但要守住一条：**Opus 不做"同一模式的第 N 遍"**。那部分既烧钱又没有品味增益。

### 1.5 成本记账：relay 下别用 `/cost`

Claude Code 的 `/cost` 是按内置 Anthropic 牌价 × token 数估算的。接第三方 relay 时，你实际付的是 relay 的价格，两者不一定相等——模型甚至可能不是你以为的那个。

所以记账来源固定为 **CC Switch 的用量面板**（本地库 `~/.cc-switch/cc-switch.db`：`proxy_request_logs` 记单请求，`usage_daily_rollups` 按天汇总），只抄美元数，不抄 token 数。协议里所有「Opus 花费」都指这个数。

推论：如果哪天你要换 relay，历史成本曲线会断——换之前先把当前任务的度量表补完。

## 2. 为什么"参照实现"是整个流程的核心

设计意图不可能被文字完整表达。模型（尤其是便宜模型）真正能继承的是**它看得见的代码**。

所以 Opus 必须留下一个"可见的正确答案"：一个达到最终质量的实例。经验规律：

> **DeepSeek 的产出上限 ≈ 参照实现的质感 - 一档。**

推论（这也是预算纪律的来源）：

- 砍预算的第一顺位是"全屏骨架"，第二顺位是"参照实现的数量"；
- **最后**才砍"规范 + 令牌 + 至少一个参照实现"。
- 让 Opus 只写规范、不写代码，等于把判断力翻译成形容词，必然掉一档。

### 2.5 为什么 P2 必须在「干净壳」里跑

Claude Code 启动时会加载全局 `CLAUDE.md` 和已启用的插件。你的环境里 `frontend-design`、`code-simplifier` 是开着的，全局 `CLAUDE.md` 还写着「发现更优方案要主动提」。

这些对 P1/P3 是优点：定调和终审本来就需要判断力。但对 P2 是灾难——P2 唯一的纪律是「照抄，不优化」，而插件和全局指令会持续把执行者往「改进」上推。执行者一旦开始判断，规范就不再是法律了。

所以分工固定：**Claude Code 只跑 P1/P3，P2 用 DeepSeek Harness**（没有这些插件和全局指令，壳更干净）。

推论：如果哪天真要在 Claude Code 里跑 P2，必须先关掉 `frontend-design` / `code-simplifier`，并在 prompt 开头显式声明「忽略全局 CLAUDE.md 的改进建议」。这不是洁癖，是防止 P2 退化成「P1 重做一遍」。

### 2.6 为什么 ARCH 轨道是同一套逻辑

有人会问：UI 靠「看得见的参照实现」，代码架构也能靠照抄吗？

能。因为架构工作的成本结构是一样的：

| | 判断（Opus） | 复制（DeepSeek） |
|---|---|---|
| UI | 配色、动效曲线、布局取舍 | 第 N 个同构组件 |
| ARCH | 边界怎么划、接口长什么样、先改哪 | 同一种机械改动的 N 个调用点 |

「抽一个 repository 接口」是判断；「把 12 个调用点改成依赖接口」是复制。「决定幂等键放哪」是判断；「给 8 个写接口补幂等键」是复制。

所以 ARCH 轨道不是另一套协议，是同一套切点原则换了一套交付物：**参照重构**替代参照实现，**接口契约 + 不变量**替代令牌，**测试 + 依赖规则**替代截图门。

### 2.7 为什么架构任务必须先有行为基线

UI 改坏了，截图能看见。架构改坏了，代码照样编译、页面照样打开——**问题可能三个月后在生产环境炸**。

所以 ARCH 轨道的第一交付物不是设计，是**测试**：characterization tests（把现状行为钉住）或 golden 测试。没有测试的区域，协议直接禁止重构。

这也是为什么 ARCH 的 G2 把 `TEST_CMD` 设成**必填**：没有测试的重构，等于在没有安全网的高空换零件。

推论：**没有测试的仓库只能做「体检」**。先让 Opus 把问题指出来，补测试，再谈重构。

### 2.8 为什么审计和闭环要分开

「指出问题」和「改完问题」是两种完全不同的成本结构：

- 审计是**判断密集型**：读代码、找证据、排严重度。贵，但产出可以复用很多轮。
- 闭环是**执行密集型**：改 N 个调用点、补测试、跑门。便宜，但要有人兜底。

混在一起做，最常见的结局是：审计列了 20 条，Opus 顺手改了 3 条，剩下 17 条没人管，代码变成「半新半旧」——比不改更危险。

所以模式上分成「体检」（只出 AUDIT，你决定修哪些）和「闭环」（审计 + 参照重构 + 铺量 + 复审）。**先看清，再决定改多少。**

## 3. 为什么规范必须是命令式的

LLM 对形容词的翻译是不可控的自由度。**每一个形容词 = 一次自由发挥 = 一次潜在的返工。**

- 可执行：`hover 时 translateY 0 → -4px，160ms，cubic-bezier(.2,.8,.3,1)，离开时瞬间回位`
- 不可执行：`hover 时微微上浮，要有呼吸感`

所以 `DESIGN.md` 里有**动效表**：一行一个动效，每行都是可测断言（属性 / 起止值 / 时长 / 缓动 / 触发 / 交错）。写不出数值的动效，说明还没想清楚，先删掉。

同理，"禁止的简化"必须写**为什么**——"这两个 SVG group 是分别做视差的"，否则执行者只会看到"这里能合并"。

## 4. 为什么用文件 + git，而不是聊天记录

聊天上下文是唯一无法跨模型审计、无法 diff、无法回滚的介质。而这次流程的每一次交接都要换模型 —— 聊天记录天然断裂。

文件 + git 换来了三件事：

1. **可回滚**：`git revert` 单个 TODO 的提交，或整体回到 `baseline/<slug>`。
2. **可度量**：提交 trailer 记录模型与 TODO ID，tag 切分阶段，事后能算"每个模型花了多少、退回几次"。
3. **可继承**：下一个仓库直接 `install.sh`，协议本身也随仓库演进。

还有一个副作用，可能比流程本身更有价值：
**因为要写下来，Opus 被迫把隐性判断变成显性规则。** 这个动作本身就会提升产出质量。

## 5. 为什么"绿着交接"必须是硬门

最贵的失败模式不是"Opus 少写了 30%"，而是**"Opus 写了 70% 但不可运行"**。

那种状态下 DeepSeek 接手会：没有参照物 → 自己发明结构 → 与 Opus 的意图偏离 → 你只能全量返工，而这一步的返工比让 Opus 写完还贵。

所以"70%"的定义必须是：**结构完整、可渲染、可交互，剩下的只是被明确列出的增强项。**
门（G1）的作用就是把"70%"从主观感觉变成"清单是否满足"。

## 6. 防退化的本质：减少需要判断的次数

六条机制（命令式规范 / 令牌唯一真相 / 冻结清单 / 禁止的简化 / NEEDS-OPUS 队列 / 截图门）其实是同一件事：

> **把 DeepSeek 需要"自己拿主意"的次数压到接近零。**

配套的两个关键设计：

- **不确定时选最保守的做法并记录假设**，而不是"停下来问"。因为问人 / 问 Opus 的上下文重建成本远高于一个保守假设。
- **批量裁决**：NEEDS-OPUS 攒 3~5 条一次问，不要一条一问。

## 7. 否决过的替代方案

| 方案 | 否决理由 |
|---|---|
| Opus 全量写完，DeepSeek 再"优化" | 最贵；且"优化"必然破坏已经定好的质感（模型无法区分"改进"和"改坏"） |
| Opus 只写规范，不写代码 | 掉一档。文字承载不了品味，参照实现才是可继承的载体 |
| 一上来就全自动脚本编排 | 自动化会**放大**模糊指令。先手工跑 2 个任务，把自己的失败模式摸清再自动化 |
| 按 token 百分比卡 Opus 预算 | 不可执行。按**交付物清单**卡才可执行（"规范 + 1 个参照实现 + 全屏可渲染"） |
| 每遇到问题就切回 Opus | 上下文重建成本 >> 答案价值。批量攒问题 |
| 用图片/截图代替规范 | 截图无法表达时序、缓动、交错节奏；截图只做验收，不做规范 |
| 在 Claude Code 里跑 P2（切 DeepSeek 供应商） | 全局 CLAUDE.md + 插件会持续建议「改进」，与「照抄不优化」冲突；换壳比改 prompt 便宜 |
| 用 `/cost` 记 Opus 花费 | relay 下按 Anthropic 牌价估算，不是你实际付的钱；改用 CC Switch 用量面板 |
| 所有任务都走 Full | 一次性页面没有复制段，走重流程是纯亏；加 Lite 档就是为了不滥用协议 |

## 8. 可调参数（你的杠杆）

| 杠杆 | 保守档 | 激进档 | 判断信号 |
|---|---|---|---|
| P1 交付物范围 | 规范 + 1 个参照实现 + 主屏 | 规范 + 3 个参照实现 + 全屏真实交互 | NEEDS-OPUS 数、POLISH 条数 |
| G2 严格度 | 只跑静态检查 | 静态 + 截图 + console | 退化是否发生在你看见之前 |
| 升级回 Opus 的阈值 | 连续 2 次失败 / 需要新视觉模式 | 任何 TODO 失败 | 返工成本 vs 一次 Opus 的问答成本 |
| P3 预算 | 0（跳过） | 15% | 跳过会掉一档质感，看你能接受与否 |

调参规则写在 `PROTOCOL.md` 第 6 节：NEEDS-OPUS > 8 或 POLISH > 20 → 切点上移；≤2 且 ≤5 → 可下移。

## 8.5 什么时候这套不值得用（ROI）

这套流程的收益 ≈ 「复制段」的规模 × 单次复制成本；成本 ≈ G1~G3 三道门 + 3 个人工检查点的时间（20~40 分钟）。

所以：

- **一次性创意页面**：别用。P1 的参照实现本身就是全部工作量，没有复制段可省，接力只是多花验收时间。
- **1~2 屏、<6 个同构元素**：走 Lite（P1 + P2，门不变），或者干脆 Opus 一把做完。
- **长尾铺量（10 个卡片 / 5 屏同构 / 断点收敛）**：Full，收益最明显。
- **纯逻辑 / 后端 / 性能**：别用。没有审美判断可买。

判断标准写死在 [README](README.md) 第 1 节和 [PROTOCOL](PROTOCOL.md) §0.1，不要凭感觉——凭感觉的结果通常是「小任务上了重流程，大任务又想省流程」。

## 8.6 ARCH 轨道的 ROI

ARCH 轨道的收益 ≈ 「机械改动」的规模 × 单次改错成本；成本 ≈ 补测试 + 写规则 + 3 个门。

- **单个 bug**：走单点，不要上闭环。根因分析 + 失败测试 + 一条修复，半小时的事。
- **跨 ≥3 模块的重构**：闭环收益最大——边界判断最贵，铺量最便宜。
- **没有测试的仓库**：先体检，别闭环。补测试的成本通常被低估。
- **「把整个代码库变干净」**：不要作为一个任务。按模块拆成多个 slug，一个 slug 一个边界。

## 9. 已知局限（诚实清单）

- **没有在真实仓库跑过**。整条链路是推导的，第一次实践大概率要改 `handoff.env` 里的门命令和 FROZEN 清单粒度。
- **relay 的 Opus 是否满血没验证过**。整套流程的上限由 P1 决定；如果 relay 给的是降级模型，后面所有纪律都只是在忠实地复制一个较低的天花板。第一次先做能力体检。
- **gate.sh 的裸值 / `transition:all` 只是警告**，不拦截。这是有意的（存量代码噪音太大），代价是「无裸值」这条纪律实际上靠人工抽查。
- **截图门只覆盖 CSS 动画 / Transition / WAAPI**。rAF、GSAP、Framer Motion 驱动的需要项目自己暴露 `window.__seek(ms)`，否则"两帧有差"这个判断会失真。
- **FROZEN 检查是路径子串匹配**（`grep -F`），不支持 glob；选择器项脚本查不到，只能靠 P2 prompt 的纪律 + 人工抽查。
- **"80~90% 效果"没有客观指标**。唯一诚实的验收是盲对比：同一需求分别用"Opus 全量"和"接力"做一版，截图并排、你不知道哪版是哪版。
- **ARCH 轨道高度依赖测试**。没有测试的仓库只能体检；补测试的成本通常比预期高。
- **架构不变量只能部分机器验证**。「多实例安全」「最终一致」「失败隔离」需要压测 / 故障注入 / 线上证据，静态检查只能覆盖依赖方向、循环、公共 API 这类结构性问题。
- **AUDIT 的严重度是主观的**。同一份代码，两个人排出来的 P0/P1 可能不一样；协议要求每条带 `file:line` 和后果，就是为了让分歧可讨论。
- **单人流程**。多人协作时 NEEDS-OPUS 队列要加 owner 字段，否则会互相覆盖。

## 10. 一句话

> **让贵模型只做"决定"和"示范"，让便宜模型只做"复制"，用 git 把每个决定固化成下一个模型能继承的东西。**
